# scenario  seed  ceilings
#
# Ceilings on the `score` line `examples/replay.rs` prints for each scenario of
# `examples/simulate.rs`, asserted by `data/bench.sh` in CI. The simulator is the only source
# with truth to score against, so this file is where the crate says how accurate the filter is
# rather than how self-consistent -- `data/manifest.txt` is the other half, on real logs with
# no truth.
#
# `key<=v` is a ceiling, `key>=v` a floor, `key=lo..hi` a two-sided bound; `data/expect.sh` owns
# the syntax and the comparison, and `data/manifest.txt` writes its expectations in the same
# language. Nothing here is two-sided yet: a ceiling is what an error wants, and the band a
# statistic wants is #89's ANEES against a chi-square bound rather than any key on this line.
#
# Each bound is the measured value plus 1 %, rounded outward -- except `scored`, which is a count
# of matched truth rows rather than a float comparison and is pinned exactly, because slack there
# would weaken the guard against scoring the wrong file. The margin is not a fudge for an unknown:
# `examples/simulate.rs` is a host tool on `std`'s `sin` and `cos`, not the `libm` crate that pins
# the filter, and since (9)-(15) every figure here is an integral over tens of thousands of steps,
# so a platform whose last bit differs moves these numbers by roughly n*eps -- about 0.2 % over
# `mission`'s 36600 epochs. 1 % is five times that, and still thirty times smaller than the
# smallest move this file has ever recorded as real (`flight`'s pos_h fell 41 % when propagation
# landed). The measured values themselves live in the commit that moved them.
#
# Every number here was measured, and a change that moves one is a change that needs a sentence
# saying what the data said -- the discipline `data/manifest.txt` already holds. A breach of a
# fraction of a percent is the margin above being exceeded, which is a real move and not drift. Moves go both
# ways, and stage 3 moved them both ways at once: `flight` tightened across the board while every
# 185 s scenario loosened by an order of magnitude. That is what dead reckoning is. Holding the
# position at zero, which is what a filter that propagates nothing does, beats integrating a
# tilt error for three minutes; it loses to it over fourteen seconds.
#
# The `seed` column pins which flight produced these numbers. `examples/simulate.rs` owns the
# seed; `data/bench.sh` checks this column against the header the generator wrote, so changing
# a seed in that table invalidates the ceilings loudly rather than re-baselining them quietly.
#
# Every departure now measures its own. `mag_disturbance` was the last to carry `mission`'s
# numbers exactly -- by design rather than by copy-paste, since it is a one-variable departure
# on `mission`'s seed and departed in a source whose `fuse_*` was a stub -- and stage 8 separated
# it: it reads `yaw` 0.726 deg against `mission`'s 0.651 and nothing else moves, which is a
# 30 deg field error costing 0.08 deg of heading because the gate refuses all 200 samples of it.
# `baro_drift` separated at (30) and is the one scenario that separates on height. Of the rest,
# the two GNSS departures separate on position: `gnss_outage` dead-reckons its gap and reads
# `pos_h` 2.37 m to `mission`'s 0.24, and `gnss_latency` 2.20. `harsh_imu` does not separate on
# position at all -- 0.243, `mission`'s ceiling -- and separates on `tilt` (1.148 deg against
# 0.576) and on `ba` (0.153 against 0.053) instead. That is what aiding a second quantity does
# to a noisy IMU: the position keys stop seeing it, and the keys that read the IMU's own errors
# are left carrying the difference on their own.
#
# What is not here is a test of the covariance itself. A ceiling pins what the filter did last
# run, so it passes a filter that grew more accurate and more overconfident at once -- the
# failure that reaches the gate, the gain and `Validity`. That needs ANEES over N seeds against
# a chi-square bound: #89. The format is already indifferent to it -- lines are read as
# `name seed pairs`, and nothing assumes one line per scenario.
#
# `gnss_latency` is what that gap looks like when it is allowed to grow. Fusing velocity left
# its `pos_h` roughly where it was, 2.31 m to 2.20, and took `nees_pos` from 6.45 to 57.18 and
# `in3s` from 0.9467 to 0.8724. The covariance shrank around an error that latency put there
# and that nothing in `R` describes (GOALS.md, "Measurement latency"; #52), so the same
# distance is now many more sigma. Every accuracy ceiling on that line tightened while its
# consistency keys went an order of magnitude the other way, which is precisely the pair of
# moves a ceiling cannot catch on its own.
#
# What every figure measures today: equations (9)-(22) propagate, and GNSS position, GNSS
# velocity, barometric altitude and magnetic heading are fused through (23)-(30) and (34)-(36)
# at `Gates::default`'s 99.9 %. No `fuse_*` is a stub any more.
#
# (30) is what `pos_v` reads now, and it moved that key and almost nothing else: 0.273 m to
# 0.083 on `mission`, 0.274 to 0.150 on `static`, 0.819 to 0.414 on `flight`. `moving_start` is
# byte-identical on all fifteen keys, which is the attribution -- it starts in motion, fixes no
# `alpha0`, and so fuses no altitude at all. The rest of `mission`'s line barely moves, because
# a barometer says nothing about the other two axes: `pos_h` unchanged at 0.240, `tilt` 0.509 to
# 0.513, `ba` 0.04902 to 0.05022.
#
# Two lines loosened, and both are honest. `gnss_outage` took `pos_h_max` from 11.93 m to 29.69,
# an excursion 2.5x worse while its `pos_h` RMSE moved 1.892 to 1.939 -- so this is variance,
# not drift. It is the gain doing what the covariance tells it: 20 s into the gap `sigma_pos_n`
# has dead-reckoned out to 95 m while the barometer holds `sigma_pos_d` at 0.14, and the
# horizontal gain of a height measurement is `rho * sigma_pn * sigma_pd / (sigma_pd^2 + R)`,
# which is 94 times whatever correlation the two carry. At rho ~ 0.1 each 0.35 m of barometer
# noise lands as 3 m of horizontal correction, and the error visibly steps at every 20 Hz
# reading. The information is still worth having: at the end of the gap the horizontal error is
# 1.39 m against 11.93 without the barometer, and `nees_pos` stays under 1 (0.817 to 0.884), so
# the covariance is not lying about the excursion it is producing.
#
# `static` took `nees_pos` from 1.06 to 2.04 -- the vertical channel is about 2x overconfident
# in sigma after a minute at rest. A 20 Hz barometer averages its own white noise down faster
# than the true vertical error falls, and what stops the error following it is the accelerometer
# bias walk, which the 15-state vector carries but the barometer cannot separate from a height.
# That is the same mechanism `baro_drift` shows at full size, and neither is a bug: it is
# GOALS.md's "barometric reference as a constant" costing what it was recorded as costing. It is
# also #89's case made twice more -- `static` grew more accurate in `pos_v` and more
# overconfident in `nees_pos` in the same diff, which is precisely the pair a ceiling cannot
# catch on its own.
#
# `baro_drift` now earns its place in the table. Against `mission`, which it matches everywhere
# else, a reference walking 0.02 m/s for 185 s puts `pos_v` at 2.052 m against 0.083 -- 25 times
# the error, and 3.7 m of drift arriving as 2 m of RMSE because the filter splits the difference
# with GNSS height. `nees_pos` goes 1.06 to 257.27 and `in3s` 1.0000 to 0.9389. The filter has no
# state that can tell a drifting reference from a climb, so it does not widen its covariance by
# so much as a sigma while being metres wrong: the error grows 25x and the uncertainty does not
# move. That is the figure GOALS.md's decision was recorded without, and the one to quote when
# revisiting it. Velocity roughly halved both error families on every
# well-behaved scenario -- `mission` `pos_h` 0.702 m to 0.240 and `vel` 0.647 to 0.190 -- and
# halved the attitude error with no attitude observation anywhere in the filter: `tilt`
# 1.010 deg to 0.509, `yaw` 1.360 to 0.636.
#
# That second number is why stage 6 was staged apart from stage 5 rather than folded into it.
# Nothing here measures attitude; the correction arrives through the velocity-attitude blocks
# (20) builds, so a tilt that did not improve would be the evidence that a sign in (17) or (20)
# is wrong -- which stage 4's Jacobian check passes either way. The consistency keys crossed 1
# from below at the same time (`nees_pos` 0.85 to 1.06), which is where a filter whose `Q` is
# conservative against its own IMU table should sit.
#
# `ba` and `bg` are the bias error itself, and they are the only keys here that fail when a
# bias estimate walks away from the bias in the IMU. The position keys absorb that for a long
# time: an accelerometer bias reaches position through two integrations, so a filter can hold
# metre accuracy against fixes while its beta-hat is wrong by most of the bias. The simulator
# injects a fixed [0.043, -0.062, 0.027] m/s^2 and [0.0021, -0.0034, 0.0012] rad/s that
# `ImuNoise::default` does not know about, norms of 0.0801 and 0.00417, so those norms are
# what a filter estimating nothing reads and the distance below them is what the aiding bought.
#
# What they measured is not what stage 6 was filed expecting, and the split into two keys is
# why it is visible at all. Fusing velocity halved the *gyroscope* bias error -- `mission` bg
# 0.00132 to 0.00067, `static` 0.00140 to 0.00078 -- and barely touched the accelerometer's:
# `mission` ba 0.05347 to 0.04902, 8 %, while `static` went the wrong way, 0.07223 to 0.07737.
# A horizontal accelerometer bias and a tilt are the same measurement to within b/g, so an
# observation of velocity pins their sum and not the split; what separates them is turning,
# and these trajectories turn gently. The gyroscope bias has no such twin, and velocity error
# is where its attitude drift arrives first. A single `bias` key would have averaged a halving
# against a wrong-way 7 % and reported a modest improvement.
#
# `moving_start` is where the coarse start's overconfidence went. Before a measurement could
# correct anything, its position and velocity priors were `Initialization`'s 1 m and 0.1 m/s
# against a truth kilometres away, and it read `nees_pos=10.30` and `nees_vel=10.59`. The first
# fix and the first velocity solution are each adopted (`Fusion::Reset`, once per quantity),
# and what is fused after them brings the pair to 1.06 and 0.45. Its `tilt` halved with
# everything else, 3.497 deg to 1.752: a coarse start's attitude prior paid down by an
# observation rather than by time.
#
# `false_valid` is zero on eight of the nine scenarios, where before velocity it was non-zero
# on every one -- 894 quantity-epochs on `mission` alone, 854 of them horizontal velocity, which
# a position fix reaches only through the correlations of (20). Observing velocity directly is
# what retired them, and a zero pinned with `<=0` is a tight gate rather than a quiet one.
# The exception is `gnss_latency`, 320 epochs with 40 of them attitude, and it is the same
# story as that line's `nees_pos`: the bar is `Config::accuracy`, and the filter now claims to
# be inside it while a late fix puts it outside.
#
# `flight` was the one line stage 5 made worse, and stage 6 is the measurement that confirmed
# the explanation written here at the time. Its window has no magnetometer, so heading starts
# 0.6 rad out; the four seconds of position fixes that correct it left 0.39 m/s of error in
# vertical velocity, and the eight seconds of dead reckoning after the fixes stop at 6 s
# integrated that into 6.8 m, taking `pos_v` from 0.72 m to 3.07. An observation of velocity
# removes exactly that error and nothing else was changed to make it: `pos_v` 3.07 to 0.819,
# `pos_h` 9.14 to 3.03, `yaw` 12.96 deg to 7.59. A heading the window observed, stage 8's, is
# the other half -- this one corrects the consequence and leaves the 0.6 rad in place.

# (34)-(36) are what `yaw` reads now, and what it buys depends entirely on what the start knew.
# Where yaw was never observed the magnetometer is the whole estimate: `moving_start` goes 3.228
# deg to 0.917 and `bg` 0.004853 to 0.002660, and `static` -- whose window carries a
# magnetometer but whose 60 s at rest let the gyroscope walk -- goes 1.715 to 0.508. Where a
# static window already fixed yaw and the flight is short, it buys nothing and costs a little:
# `mission` goes 0.644 to 0.651, `tilt` 0.519 to 0.576 and `bg` 0.000677 to 0.001013. A heading
# carrying 3.1 deg of noise per sample has nothing to tell a filter whose alignment knew yaw to
# 0.6 deg, and the corrections it makes reach tilt and gyroscope bias through the correlations
# (20) builds. Both readings are the same equation; which one a vehicle gets is a property of
# its start, not of the filter.
#
# `nees_att` rose on every line -- 0.0353 to 0.2005 on `mission`, 0.1254 to 0.2263 on
# `moving_start` -- and that is the direction that wants watching rather than the one that
# wants fixing. It is the move stage 5 made on `nees_pos` (0.0118 to 0.85): a key sitting three
# orders below 1 is a covariance with nothing in it, and an attitude that is finally observed
# approaches 1 from below. It is still below. #89 is what reads it as a bound rather than a
# ceiling.
#
# `gnss_latency` is the one line that loosened on a claim rather than a number: `false_valid`
# 340 to 418 and `false_valid_att` 57 to 122. The attitude covariance came down where the
# attitude error did not, because a late fix is wrong by the distance flown in the delay and
# nothing in `R` says so (GOALS.md, "Measurement latency"; #52) -- so the filter calls an
# attitude valid that truth puts outside `Accuracy`. It is the same mechanism the line already
# carried on position, now reaching attitude because attitude is now observed. #89 owns it; #52
# owns the cause.
#
# What (36') is worth is measured on `moving_start`, and it is the difference between a stage
# that ships and one that does not. Pricing the levelling error into `R` took that line from
# `tilt` 2.653 deg to 1.665, `yaw` 3.777 to 0.917, `nees_att` 1.634 to 0.226, and 840
# falsely-valid attitude quantity-epochs to zero. Without it the filter reads a heading through
# a tilt it is unsure of, prices the result at the magnetometer's own noise, and believes the
# answer -- which on a coarse start is a filter claiming an attitude it does not have.
#
# The adoption is priced by (36') as well, and that is where the term is worth the most: the
# first heading is levelled by the worst tilt the filter ever holds. On `moving_start` the
# adopted yaw variance is 0.582 rather than the magnetometer's own 0.01 -- sigma 0.76 rad
# against an `Accuracy::heading` of 0.5236 -- so the heading is established and reported
# invalid, rather than established and believed. That, with the (41) the adoption now applies
# to the attitude rows it does not replace, is `tilt` 1.720 deg to 1.665, `yaw` 0.940 to 0.917
# and `nees_att` 0.2310 to 0.2263.
#
# The two bias keys are what paid, and both ceilings loosened for it: `ba` 0.05514 to 0.05791
# and `bg` 0.002577 to 0.002660. A yaw the filter is honestly unsure of takes more of each
# velocity correction and leaves less for the gyroscope bias, which is the split (20)'s
# attitude-bias block decides. Attitude accuracy and attitude consistency both improved in the
# same diff; the biases gave up 5 % and 3 % to pay for it.
#
# Splitting (28)'s gate into a horizontal `Gate<2>` and a vertical `Gate<1>` (`GnssFusion`) is a
# loosening everywhere GNSS is fused, and a small one: `mission` `pos_h` 0.240 to 0.244 and
# `nees_pos` 1.0365 to 1.0539, with `harsh_imu`, `mag_disturbance`, `gnss_outage` and
# `moving_start` moving by the same few tenths of a percent. It is the price of two tests where
# there was one. Each half is gated at P999 and so turns down one good half in a thousand, where
# the joint test turned down one fix: `mission` rejected 1 fix and now rejects 2 horizontal
# halves and 2 heights, out of 915. Whenever both halves are accepted the two sequential updates
# are the joint one, `R` being diagonal. What it buys is on real data rather than here: a height
# the estimate disagrees with no longer costs the horizontal fix beside it (`src/config.rs`,
# `Gates`).
#
# (30') estimates the barometric reference rather than holding it (#119), and every line with a
# barometer moved, most of them looser in `pos_v` and tighter in `nees_pos`. `baro_drift` is the
# line the change is for: `pos_v` 2.053 m to 0.284, `nees_pos` 257.52 to 1.19, `in3s` 0.9389 to
# 0.9999 -- the drift is followed rather than split with GNSS height. `static` goes 2.04 to 1.02 in
# `nees_pos`, and the explanation this file carried for its 2.04 -- the accelerometer bias walk
# the barometer cannot separate from a height -- was at most part of it: with the offset
# estimated at `q_b = 0` it reads 1.92, so what took it to 1.02 is the reference being allowed to
# walk. The cost is `pos_v` on every line whose barometer does not drift, which in this simulator
# is all but one: `mission` 0.083 m to 0.249, `static` 0.150 to 0.215. At PX4's 0.13 m/s/sqrt(Hz)
# the reference walks away from what the barometer knew and GNSS height carries the low
# frequencies. That is the default the corpus argued for (GOALS.md, "Barometric reference as an
# estimated offset"), and a simulator whose barometer never drifts is the one place it looks
# like pure loss. `moving_start` and `2c42096b` are unmoved, since a start in motion still fixes
# no reference until #115.
